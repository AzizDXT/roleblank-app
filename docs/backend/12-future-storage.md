# 12 — Future Object Storage / File Uploads

**Status: not built, and deliberately so.** There is no upload endpoint, no multipart
handler, no filesystem write path, and no static file server. The API accepts only
`application/json` and rejects `multipart/form-data` outright, which is why
`02-threat-model.md` §5 can list **unrestricted file upload** and **path traversal** as
*not applicable* rather than as mitigated.

There is **no placeholder endpoint** — not a stubbed `POST /files`, not a "temporary" local
disk write, not a dev-only route behind a flag. A half-built upload path is the most
reliably exploited thing a backend can contain, and an endpoint that exists is an endpoint
that eventually gets enabled. This document records what must be true before one is written.

## 1. The split: PostgreSQL holds metadata, the object store holds bytes

| Concern | Where | Why |
| --- | --- | --- |
| File identity, ownership, project/task linkage, authorisation inputs, scan state, versions, audit references | PostgreSQL | These are relational facts that participate in transactions, foreign keys, and the CLIENT visibility predicate. They must be queryable and consistent with the rest of the domain |
| The bytes | S3-compatible object store | Large opaque blobs in PostgreSQL bloat the primary, inflate every backup and restore, and put unbounded payloads through the connection pool that serves the hottest authentication query in the system |

The database row is authoritative for **whether a file exists** as far as the application is
concerned. An object present in the bucket with no committed metadata row is invisible and
is garbage-collected; this ordering is what makes an interrupted upload a no-op rather than
an orphaned, unauthorised, downloadable object.

## 2. Abstraction boundary: no vendor in the domain layer

One trait — an object-store port — with the operations the domain actually needs: put,
get, delete, head/stat, and presign for read and write. Candidate implementations:
**Cloudflare R2**, **MinIO** (local development and self-hosted), **AWS S3**. This follows
the same rule as `trait RateLimiter` and `trait MailProvider` in `01-architecture.md` §4: an
abstraction is introduced when a second implementation is already known, and not before.

What that means concretely:

- No service or repository mentions a bucket name, a region, an endpoint URL, or a
  vendor SDK type. Those are configuration and adapter-internal.
- The domain deals in an opaque object key and a byte stream. Vendor-specific features
  (lifecycle rules, storage classes, replication) live in infrastructure configuration, not
  in application code, because a feature only one candidate supports becomes lock-in.
- Development uses MinIO against the same trait, so the code path exercised in tests is the
  code path that runs in production — not a filesystem shim that behaves differently in
  every way that matters (atomicity, key semantics, presigning).
- The bucket is **private with no public read**, verified at startup rather than assumed.
  Every read is mediated (§6). A misconfigured public bucket makes every control in this
  document irrelevant at once.

## 3. Object keys are generated by the server

**A client never supplies, influences, or suggests a storage path.** The key is derived
server-side from a UUIDv7 file id (`01-architecture.md` §6) plus a scoping prefix the server
computes, and the original filename is stored as *metadata in PostgreSQL only* — a display
label, never a path component.

Two failures this prevents:

- **Traversal.** A client-supplied key of the form `../../other-tenant/contract.pdf`, or one
  containing encoded separators, null bytes, or Unicode normalising to a separator, escapes
  the intended prefix. Object stores are flat namespaces, but prefixes are used as tenancy
  boundaries in lifecycle rules, IAM policies, and listing operations, and every layer that
  interprets a key parses it slightly differently. Not accepting the input removes the entire
  parser-differential class rather than trying to sanitise it.
- **Overwrite.** A client that can name a key can name one already in use and replace another
  principal's document with its own — a silent integrity attack that looks like a successful
  upload in every log. A server-generated, unique key makes collision impossible rather than
  merely unlikely.

Additional consequences: keys must not be guessable (the UUIDv7 randomness carries this) and
must never be treated as authorisation. Possessing a key grants nothing, exactly as
possessing a project UUID grants nothing (`04-authorization.md`). Every access is decided by
the evaluator against the metadata row.

## 4. Type verification: allowlist **and** content inspection

Both, in this order, and neither alone:

1. **Extension allowlist**, closed and short, defined per attachment context. A denylist is
   wrong because the set of dangerous types is open-ended and grows with every client
   application that renders a file.
2. **Content-based verification** — magic bytes / structural sniffing of the received stream —
   asserting the actual content matches the claimed and allowlisted type. A file named
   `report.pdf` whose bytes are an HTML document with a script tag is rejected, not stored.

**The `Content-Type` header is never trusted for any decision.** It is client-controlled
free text with no relationship to the bytes that follow. It may be recorded as an
observation; it may not gate storage, drive the extension check, or be echoed back as the
response `Content-Type` on download (§6).

The residual risk is stated plainly rather than waved away: magic-byte checks confirm a
plausible header, not that a file is safe. A structurally valid PDF or DOCX can still carry
an exploit for the viewer that opens it, and polyglot files that satisfy two format checks
at once exist. Content verification narrows the class of attacks; the scanning hook (§8) and
the download hardening (§6) cover what remains, and none of these makes an uploaded file
trustworthy.

## 5. Size limits, enforced twice

| Layer | Enforcement | Why it is not sufficient alone |
| --- | --- | --- |
| Edge proxy | Hard request-size cap on the upload route, refusing before bytes reach the application | The proxy is bypassed if a client uploads directly to the object store using a presigned URL |
| Signed policy | The presigned upload policy itself carries a maximum content length, so the object store rejects an oversized body | The policy only binds direct-to-store uploads |
| Application | The metadata row records the expected size; the finalisation step verifies the stored object's actual size (via head/stat) against it before the file becomes usable | A client can lie in the metadata request |

The global 256 KB JSON body limit (TH-33) stays untouched: upload bodies do not travel
through the JSON path. The upload route is a separate, explicitly bounded surface, and the
default answer to "how large" is the smallest size that satisfies a real requirement.

Streaming, not buffering: the server must never accumulate a whole file in memory to
validate it. Bounded chunk reads, with the limit enforced as the stream is consumed, so
exceeding it aborts mid-transfer instead of after a successful allocation.

## 6. Authorisation on every read and write, including presign

A presigned URL is a **capability** — a bearer credential in a URL that anyone who obtains
it can redeem, with no session, no principal, and no evaluator behind it. That makes the
moment of issuance the security decision:

- **Issuing a presigned URL is authorised exactly as the equivalent direct operation.**
  Presigning a read runs the same object-level check as reading the file; presigning a write
  runs the same check as creating it. There is no "the URL itself is the check".
- **Presigned URLs are short-lived** — minutes, sized to the operation, not hours. They land
  in browser history, `Referer` headers, and proxy logs by the same mechanism that makes
  query-string tokens unacceptable elsewhere (TH-36, `11-future-realtime.md` §4). Short
  expiry bounds the damage; it does not eliminate it, which is why the URL must also be
  scoped to a single object and a single method.
- **Presign issuance is audited** with the file id, the principal, and the operation. The
  audit trail must show who was *granted the capability*, since the redemption happens at the
  object store where the application cannot see it.
- **CLIENT principals go through the visibility predicate** (`04-authorization.md` §9) before
  any URL is issued — a file attached to a project a client cannot see must produce the
  `404` form, not a presigned link.
- **Revocation is weak for an outstanding presigned URL** and this is a carried residual risk,
  not a solved problem: once issued, the URL is valid until it expires regardless of session
  revocation or a permission change. This is the same property that made JWTs unacceptable
  for sessions (ADR-002/ADR-005), and it is the reason expiry is measured in minutes and the
  option to proxy downloads through the application — where the per-request check still
  applies — must remain available for sensitive attachment contexts.

Download hardening, wherever the bytes are served: `Content-Disposition: attachment` with a
sanitised filename, a server-determined `Content-Type` (or `application/octet-stream`),
`X-Content-Type-Options: nosniff`, and a restrictive `Content-Security-Policy`. Serving
user-supplied bytes from an origin that also serves the application is how an upload feature
becomes stored XSS; a distinct download origin is strongly preferred.

## 7. File states

A file is not downloadable because it uploaded successfully. It is downloadable because it
reached a state that says so.

| State | Meaning | Downloadable |
| --- | --- | --- |
| `PENDING` | Metadata row created, upload not finalised | No |
| `QUARANTINED` | Bytes stored, awaiting or failing scan | **No** — the default after upload |
| `AVAILABLE` | Verified and scanned clean | Yes, subject to authorisation |
| `REJECTED` | Failed type verification or scanning; bytes scheduled for deletion | No, permanently |
| `DELETED` | Soft-deleted metadata; bytes removed | No |

The state is a column on the metadata row and is part of every query that resolves a file,
so "downloadable" is a database predicate rather than an application-layer `if` that one
call site can forget.

## 8. Scanning hook and quarantine

Uploads land in `QUARANTINED` by default. A scanning hook — an interface, not a specific
product, with ClamAV or a hosted scanner as candidate implementations — moves a file to
`AVAILABLE` or `REJECTED`.

- **Fail closed.** If the scanner is unavailable, files stay quarantined. The failure mode is
  a feature that stops working, not a feature that stops checking.
- **Scan before availability, never after.** A file that is downloadable while a scan is
  pending has already been distributed by the time the verdict arrives.
- **The scanner is an outbound integration**, so it is subject to the egress rules recorded
  in `06-security-controls.md` §Egress and referenced in `10-future-ai-mcp-security.md` §9 —
  an allowlisted destination, explicit timeouts, bounded response handling, and no
  user-controlled URL.
- **Rescanning is possible.** Signature databases improve; a file that passed last month can
  be re-evaluated and moved back to `QUARANTINED`.
- Scanning reduces exposure to known malware. It is not a guarantee about unknown content,
  and it is not a substitute for §4 or for the download hardening in §6.

## 9. Metadata row, sketched

Fields the row must carry, without prescribing the migration:

| Field | Purpose |
| --- | --- |
| `id` (UUIDv7) | File identity; the basis of the object key |
| `object_key` | Server-generated; unique; never client-influenced |
| `owner_user_id`, `created_at` | Attribution |
| attachment context (`project_id` / `task_id` / …) | The resource the evaluator authorises against, and the join the CLIENT visibility predicate traverses |
| `client_visible` | Per-file, defaulting to `false`, mirroring `tasks.client_visible` — attaching a file to a shared project must not expose it |
| `original_filename` | Display only; sanitised on output; never a path |
| `declared_content_type`, `verified_content_type` | The claim and the finding, kept separate on purpose |
| `size_bytes`, `checksum` | Verified against the stored object at finalisation; integrity and deduplication |
| `state` | §7 |
| `scan_result`, `scanned_at` | §8 |
| `deleted_at` | Soft delete, with byte deletion as a separate reconciled step |

Deletion is two-phase: the metadata row is soft-deleted transactionally (immediately
removing access), and a reconciliation job removes the bytes. Deleting the object first
would leave a committed row pointing at nothing on a failure between the two, and there is
no distributed transaction across PostgreSQL and an object store to lean on.

## 10. Rules that must never be relaxed

1. No upload endpoint ships before §4 (allowlist **and** content verification), §5 (size
   limits at both layers), §3 (server-generated keys), §6 (authorisation on every read,
   write, and presign), and §8 (quarantine before availability) are all implemented and
   tested.
2. `Content-Type` from the client never gates anything.
3. No client-supplied path, key, prefix, or filename component ever reaches the object store.
4. The bucket is never publicly readable.
5. A presigned URL is issued only after the same authorisation decision as the direct
   operation, is scoped to one object and one method, and is short-lived.
6. Quarantine is the default state after upload; the scanner failing keeps files quarantined.
7. No placeholder, dev-only, or flag-gated upload route exists in the meantime — the
   `02-threat-model.md` §5 rows for unrestricted upload and path traversal stay accurate
   until this document is implemented in full, at which point both rows move from *not
   applicable* to *mitigated*, with their own threat-matrix entries and tests.
